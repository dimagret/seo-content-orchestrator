# Supervised subscription rail — Standard design

## Decision

Use `gpt-5.6-terra via openai-codex` only inside a visible Hermes session. The SEO Orchestrator never invokes, proxies, retries, or attempts to recover a Codex provider request. It prepares deterministic stage packets and accepts a result only after an operator binds an observed session completion to the exact packet.

This preserves the full content-quality contour while intentionally not claiming unattended external-job durability.

## Scope and exclusions

In scope:

```text
frozen brief
→ safe acquisition
→ normalized evidence
→ stage packet
→ supervised Hermes stage
→ local result binding
→ deterministic QA
→ immutable local artifact
→ manual review
```

The first canary contains exactly four supervised model stages:

```text
outline → draft → critic → revision
```

Out of scope: `hermes proxy`, direct provider HTTP, OAuth/auth file access, API keys, new Hermes listeners, Telegram, Sheets, n8n, publication, deployment, background retries, and raw hidden-reasoning storage.

## Components

### 1. `StagePacketBuilder`

A deterministic local component in the SEO Orchestrator. It receives only a valid frozen job, approved plan, normalized evidence, and target stage. It produces a canonical bounded packet:

```text
job_id, company_id, stage_id, sequence,
approval_record_id, approved_plan_fingerprint,
snapshot_hash, evidence_hash, prompt_template_version,
provider_id=openai-codex, model_id=gpt-5.6-terra,
input_hash, structured_prompt
```

`input_hash` covers every displayed field. Packets have no arbitrary destination, tool definition, URL, provider, model, header, or credential field.

### 2. Session execution card

The operator opens the packet in the current Hermes session and explicitly asks to execute that one stage. The prompt requires a bounded structured response that includes `job_id`, `stage_id`, `input_hash`, and the stage payload. A provider/model string generated by the model is non-authoritative and is not used as proof.

This is a visible subscription use, not a machine-to-machine provider request. The subscription session remains the owner of model interaction and credentials.

### 3. `ObservedCompletionBinder`

A local command accepts a result file only when the operator attests that it was observed in the designated session with the expected provider/model selected. It validates the packet identifiers and input hash before persisting that redacted operator attestation plus the bounded stage payload. The attestation is an explicit human control, not a cryptographic claim about the consumer backend. The binder cannot submit a packet to Hermes or invoke a model.

### 4. `StageAcceptanceChecker`

Deterministic code validates schema, maximum sizes, citations/evidence references, forbidden secret-like content, the expected packet binding, and stage-specific constraints. The configured session provider/model remains an operator-attested gate because the consumer transport exposes no durable, machine-verifiable execution record. A failed check never advances the job.

## State machine

```text
PACKET_READY
  → AWAITING_OPERATOR_EXECUTION
  → COMPLETION_SUBMITTED
  → ACCEPTED | REJECTED
  → next PACKET_READY | FINAL_QA | FAILED
```

No state transition sends a provider request.

### Crash/recovery

- Before operator execution: the packet remains `AWAITING_OPERATOR_EXECUTION`; it can be opened again without a model call.
- After an observed session result but before binding: operator may bind that exact result against its input hash.
- If it is unknown whether the session executed the packet: set `OPERATOR_RECOVERY_REQUIRED`; do not create a replacement packet or retry.
- A replacement stage requires an explicit operator decision and records a new sequence/attempt. It is never automatic.

### Cancel

`CANCEL_REQUESTED` prevents new packets. Because the consumer transport has no proven upstream cancel semantics, a session-level stop is recorded only as an operator observation. The job is never marked as a successful cancellation of upstream work.

## Quality controls

1. Freeze the brief, approved plan, URL allowlist, and normalized evidence before `outline`.
2. Every stage has one immutable input hash and one explicit session execution gate.
3. `critic` receives the frozen evidence and draft, not authority to invent facts or change scope.
4. `revision` accepts only valid critic findings and validated evidence references.
5. Final deterministic QA remains authoritative over SEO rules, citations, evidence/claim binding, destination, and artifact integrity.
6. The artifact stays local and immutable; manual review is mandatory before any future delivery decision.

## Approval boundary

A future real canary still requires a separate G4 approval that names the frozen brief, exact four packet sequence, model, provider, URL allowlist, execution session, token ceilings, expected subscription use, and local-only destination. Design approval does not authorize a model stage.

## Verification plan

Before any subscription use, run local tests only:

1. canonical packet/hash determinism and changed-payload rejection;
2. invalid stage/approval/snapshot binding and missing operator-attestation rejection;
3. wrong-company and wrong-session completion rejection;
4. state-machine tests for crash before execution, after execution/before binding, unknown execution, cancel, and no automatic retry;
5. structured-result schema, size, citation, hidden-reasoning, and secret-like-content rejection;
6. final artifact can be created only after all four accepted stages plus deterministic QA.

## Definition of done

The implementation is ready for a G4 canary only when all local tests above pass, the result contains no direct provider transport code, and a reviewer can prove from the state ledger that no stage was ever retried or advanced without an operator-attested, packet-bound observed completion.

## Implementation hardening addendum

The local ledger's event authority is not the mutable `status` projection or the greatest
SQLite `event_id`. Every event has a per-job sequence, predecessor hash, canonical envelope
hash, and keyed MAC. The job row stores the exact event count and current hash/MAC head;
append and head changes are constrained in one SQLite transaction. Every status-sensitive
read verifies the complete chain and the private key commitment before using the projection.
It also validates each event's exact details schema and reconciles authenticated
`PACKET_PREPARED`/`COMPLETION_ACCEPTED` commitments with every canonical packet and completion
row. The job packet head, frozen context/binding, predecessor completion links, final-QA input,
and artifact projection must all agree with that replay. Finalization reads the revision only
after this reconciliation, so replacing a canonical completion row and its self-hash while
leaving the authenticated event chain untouched fails closed.

The 256-bit integrity key is a separate owner-only, single-link file beside the derived
ledger. Its SHA-256 commitment is immutable ledger metadata. Missing, replaced, aliased,
permission-weakened, malformed, or mismatched key material fails closed. Therefore a direct
SQL writer cannot authorize a recovery/cancel transition by appending a merely
self-consistent event and editing `supervised_jobs.status`.
